# Модель данных

Всё хранится в JSON. Три корневых типа объектов.

## Корневые типы

### Event Object

Событие — то, что произошло.

    id, name, description, type,
    when        — тик, когда произошло
    who[]       — id участников
    where       — составной путь Plane_id:World_id:region_id
    importance  — значимость, для ранжирования при доборе
    refs[]      — ссылки на связанные Memory Object

`where` хранит весь путь целиком, а не только регион. Это намеренная
денормализация: позволяет фильтровать «все события в этом мире» без обхода
графа. Безопасна потому, что событие — исторический факт: регион не переедет
в другой мир задним числом. На изменяемые сущности приём не переносится.

### Memory Object

Постоянная сущность мира: кто правит, где что лежит, кто есть кто.

    id, type (класс), name, ...

`type` играет роль тега: по нему берут «все объекты такого рода».

### Battle Object

**Хранилище префабов для инициализации боя.** Не отдельная жизнь объекта,
а заготовка, из которой бой собирается.

    id, type (класс), name, isBreakeble, pos, size

У `person` и `mob` есть поле `battle`, указывающее на их боевой префаб.
Возможность позвать префаб напрямую тоже сохраняется — для засад и
статистов, у которых нет своей записи в памяти.

## Классы

| Класс | Назначение |
|---|---|
| `Plane` | план бытия, верх мультивселенной; содержит миры |
| `domain` | домен, содержит `SelectionTree` |
| `skill` | навык, содержит описание |
| `person` | разумное существо, см. `Person/` |
| `mob` | неразумное наполнение природы |
| `Combatant` | боевой префаб существа: контейнер характеристик |
| `Tile` | боевой префаб клетки поля |

`Culture` и `Religion` слиты в `Ideology` — сознательное упрощение,
`god` внутри идеологии ложится на лор с верой мирян.

### Combatant и Tile

**`Combatant`** — контейнер характеристик существа, префаб для боя. Привязан
к своему Memory Object (`person` или `mob`).

    properties, effects, hit, speed, skills

**`Tile`** — префаб клетки поля боя: вода, трава, преграды (колонны,
стены), следы заклинаний. К памяти **не привязан**, живёт только
внутри боя.

    properties, hit

### Способности

Разделение булево, на каждом уровне:

    canDamage / notCanDamage
      can:    damage, effects, properties, rangetype
      heal / notHeal
        heal:    effects, properties, rangetype
        notHeal: effects, properties, rangetype

`damagetype`, `healtype`, `heallight` убраны — тип уехал в `properties`.

### properties

Сам по себе класс:

    тип навыка
    особенности     — например, чем этому можно противодействовать
    вложенные конструкторы функций

> **Риск свалки.** Сюда уже сложены тип навыка, особенности, конструкторы
> функций и состояние носителя домена. Нужен тег `kind`, иначе через
> полгода не разобрать, что внутри.

## Мир

### Territoryis

Сетка 100×100 регионов по 100 км². Регион содержит:

    население, ресурсы (еда, товары, золото), биом

Простой бот распределяет ресурсы по условным правилам: товары дают больше
еды, еда — больше людей, люди отдают деньги и потребляют еду и товары.

> **Десять тысяч регионов — это симуляция уровня Paradox.** Каждый тик
> бот проходит по миллиону квадратных километров, и 99% этой работы
> игрок никогда не увидит.
>
> Нужен **LOD симуляции**: регион рядом с игроком считается полностью,
> дальше — агрегированно на уровне `Gouverment`, далеко — заморожен
> и досчитывается одной формулой при визите. Так делают Dwarf Fortress
> и RimWorld.

### Gouverment

    тип правления, описание,
    глава (если есть), наследник (если есть),
    подвластные region, законы,
    армия: Army → Division { id, name, manpower, pos(region), armament }

### Ideology

    rules,
    население (распределение по регионам),
    god (если религия; в светской идеологии — наставник)

## Состояние носителя домена

Бывший `state_player`. Принадлежит **любому** носителю домена, не только
игроку. Хранится в `person.properties`, если персонаж — бог.

    domains, skills, ash, constellations, ...

## Направление рёбер

**Связь хранится в одну сторону. Обратное направление даёт индекс,
а не второе поле.** Два поля — это два источника правды, которые разъедутся
молча: перевёл регион другому правительству, забыл обновить вторую сторону.

Сторону выбирают по кардинальности: **поле живёт там, где «много»**.

| Правильно | Неправильно | Почему |
|---|---|---|
| `region.gouverment` | `Gouverment.regions[]` | десятки правительств против 10 000 регионов; массив на тысячи id переписывается при смене владельца одного региона |
| `Division.army` | `Army.divisions[]` | то же |
| `World.plane` | `Plane.worlds[]` | то же |
| `Gouverment.world` | `World.gouverment` | у мира много государств, а не одно |
| `Ideology.world` | `World.ideology` | у мира много идеологий |
| `person.ideology` | `Ideology.followers[]` | вера — свойство человека, едет с ним |

Обратный индекс строится за один проход при загрузке и делает обход
в обратную сторону бесплатным — см. `04-memory.md`.

## Где правило не работает

Кардинальность — эвристика, а не закон. Четыре случая, где решает логика.

**Ребро несёт данные.** Доля населения региона, исповедующая идеологию, —
это не ссылка, а ссылка с числом. Ни на одну сторону как `id` не ложится.
Живёт там, где меняется: `region.faiths = {ideology_id: доля}` — меняется
вместе с регионом каждый тик.

**Связь симметрична.** `person.family[]` — «много» с обеих сторон, правило
молчит. Либо список с обязанностью писать его симметрично, либо отдельная
запись отношения `{a, b, kind}`. Второе честнее, если родство будет
что-то значить механически.

**Связь один к одному.** «Многой» стороны нет, решает принадлежность:
`World.territoryis` — сетка принадлежит миру; `Gouverment.глава` —
правитель есть свойство государства, а не государство свойство человека.

**Не знаешь, одно или много — делай много.** Риск несимметричен.
Смоделировал «много», а на деле одно — индекс просто вернёт список из
одного элемента. Смоделировал «одно», а понадобилось много — ломается
схема, данные и сейвы. Именно на этом здесь и была ошибка
с `World.gouverment`.

**Исключение: списки на неизменяемых записях.** `Event.who[]` живёт на
событии, и это верно — событие владеет своим составом и не меняется
после записи.

## Battle Object и рассинхрон

Поскольку `Battle Object` — это префаб, а не вторая жизнь сущности,
результат боя обязан **писаться обратно** в Memory Object. Иначе NPC,
убитый в бою, останется живым в памяти мира.

Правило: бой читает из префабов, но исход применяется к сущностям.
